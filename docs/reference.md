## Webflow CMS custom fields (Parts collection)

| Field | Slug | Type | Purpose |
|---|---|---|---|
| Price Status | `price-status` | Option | Blank / "On Sale" / "New Price" — drives the was/now price display and which badge shows. Added 9 Sep 2026, replaces the old `on-sale` Switch field (still present but unused and un-deletable, see Housekeeping in `CLAUDE.md`). |
| Sale / New Price | `sale-price` | Number | The new price to display when Price Status is set. Renamed from "Sale Price" 9 Sep 2026 — slug is unchanged, so old references to `sale-price` still resolve to this field. Leave blank when Price Status is blank. |

**This field does not affect what a customer is actually charged.** The real, authoritative price is whatever's set on the item in Zoho — Moni updates that manually and separately. These two fields are purely a front-end display layer (was/now price + badge); `worker.js` has no awareness of them at all. If the displayed "new" price and the real Zoho price ever get out of sync, a customer could see a different number than what they're actually charged — keep both updated together when running a sale/price change.

## Key website gotchas — read before debugging

- **Form spam came from bots posting straight to Webflow, not through the page.** Found 24 Nov 2026: 98 of the last 100 Webflow form submissions had no `company_website_url` field, which the sitewide honeypot (Section 9) adds to every form in the browser, so they never loaded the page and our JS never ran. The off-screen `Quote Request Form` component (on every page, never visible except on quote review, which uses the Worker) was the main target (58/100). Fix: every real form now posts to the Worker, and Moni removed **Email Notifications** and **Zoho Flow** from the forms' "Send to" in Webflow, so native submissions go nowhere except the Webflow Forms dashboard. **"Send to" destinations are shared site-wide**: deleting one from any form removes it from all forms. Don't re-add Email Notifications. Next step if spam reaches the Worker emails: Cloudflare Turnstile (portal window).
- **Sitewide `section { padding-left/right: 0 !important }` in `global-styles.css`** strips side padding from every `<section>`, including ones inside Embeds. Override with `section.your-class { padding: ... !important }`.
- **Webflow's own form email template labels every form "New Webflow Quote Request"**, which is misleading. Irrelevant now that notifications are off.
- **Resend rejects `reply_to` addresses without a dot after the @** (e.g. `test@testimonial`), even though the browser's `type="email"` accepts them. The Worker returned 500 for this on `/testimonial-form`. Portal fix suggested: validate email and return 400 before calling Resend, and don't echo Resend's error `detail` to the client.

- **`global-styles.css` and `global-footer.js` are served by the Cloudflare Worker `empty-cake-b32dtwx-assets`, which proxies live from GitHub `main` on every request — it does NOT store its own copy.** Corrected 19 Jul 2026 — an earlier version of this doc claimed the opposite (that the Worker had its own copy and needed manual updating), which was wrong and cost a wasted step during the nav-redesign go-live. The Worker's actual source (confirmed by reading it directly in the Cloudflare dashboard):
  ```js
  export default {
    async fetch(request) {
      const url = new URL(request.url);
      const path = url.pathname;
      let file;
      if (path.includes('global-styles') || path.endsWith('.css')) file = 'global-styles.css';
      else if (path.includes('global-footer') || path.endsWith('.js')) file = 'global-footer.js';
      else return new Response('Use /global-styles.css or /global-footer.js', { status: 404 });
      const ghUrl = `https://raw.githubusercontent.com/twx26mon/webflow-footer-scripts/main/${file}`;
      const response = await fetch(ghUrl, { cf: { cacheEverything: false } });
      const text = await response.text();
      return new Response(text, {
        headers: {
          'Content-Type': file.endsWith('.css') ? 'text/css; charset=utf-8' : 'application/javascript; charset=utf-8',
          'Cache-Control': 'no-cache, no-store, must-revalidate',
          'Access-Control-Allow-Origin': '*'
        }
      });
    }
  };
  ```
  **Practical implications:** (1) merging to `main` and pushing is the *entire* deploy step for both files — there is no separate "update the Worker" action, ever; (2) `main` is effectively an instant-deploy production branch for this repo — treat a push to it with the same care as a live deploy, since it takes effect immediately with no cache delay (`no-cache, no-store, must-revalidate`); (3) to test staging changes without touching `main`, still temporarily swap the Webflow head/body code to `https://cdn.jsdelivr.net/gh/twx26mon/webflow-footer-scripts@[commit-hash]/[file]` (jsDelivr, pinned to a commit hash, never a branch name — branch-based URLs cache aggressively) — this part of the old advice was correct; (4) once a `staging` branch is merged and confirmed, revert the Webflow head `<link>`/body `<script>` from the jsDelivr test URL back to the permanent Worker URLs (`https://empty-cake-b32dtwx-assets.monica-6b5.workers.dev/global-styles.css` and `.../global-footer.js`) — nothing else needs touching.
- **Don't trust `wrangler init --from-dash` to pull an existing Worker's real source on this setup** — tried 19 Jul 2026 to fetch `empty-cake-b32dtwx-assets`'s actual code before editing it, but even with `-y`, it silently fell through to the generic `npm create cloudflare` scaffolding wizard and produced an unrelated "Hello World" template instead of the live script. Caught before anything was deployed by checking the pulled files, but don't assume this command is safe to deploy from — go read the real code first (Cloudflare dashboard → Workers & Pages → the Worker → Edit code) if you need to see what's actually live.
- **A changelog note saying something was "fixed" doesn't mean it's live** — the Tawk chat-widget `</script>` fix was marked fixed 16 Jul 2026, but when the live Webflow Site Settings footer code was actually read via the Webflow API on 19 Jul 2026 (while updating the head/body code URLs post-launch), the same unclosed `<script src="...global-footer.js">` bug was still sitting there, unfixed, in production. Re-applied and re-verified directly against the API this time rather than trusting the earlier note. For Webflow custom code specifically (a manual paste-in field, no git history to check), verify the *actual current* content via `data_scripts_tool > get_site_freeform_code` before relying on what a doc says was done.
- **Raw GitHub CSS URLs don't work in browsers** — `raw.githubusercontent.com` serves files as `text/plain` and Chrome refuses to apply them as stylesheets. Always use jsDelivr for testing.
- **Webflow CSS class names:** always inspect the live DOM before writing selectors — Webflow's designer labels often differ from the real class names. Key info bar classes: `.header-contact-container` (the desktop layout wrapper), `.header-phone-wrapper`, `.header-email-wrapper`, `.header-dealer-wrapper`, `.social-icon-container`, `.header-social-text h3` ("Follow Us" is an h3, not `.text-block`). Info bar link text uses `a.topbar-text` (not `.nav-top-link`). Navbar dropdown toggle is a `div.w-dropdown-toggle.nav-link`, not an `a` element.
- **`getSession()` is duplicated intentionally** — Section 0 and Section 2 of `global-footer.js` are separate IIFEs with separate scopes. Section 2 has its own `getSession()` at the top of the IIFE. Do NOT remove it thinking it's a duplicate — the cart will fail silently without it.
- **Quote cart site head CSS** — the CSS currently pasted into Webflow Site Settings → Head Code for the cart panel is saved in `quote-cart-site-head-code.css` in the `webflow-footer-scripts` repo (for reference only — it is NOT served from there). Any cart style changes must be made in that file and then copy-pasted into Webflow Site Settings manually.
- **`w--current` on dropdown toggles** — Webflow adds `w--current` to `<a>` sub-links inside dropdown lists, NOT to the dropdown toggle `<div>`. The `activateDropdownNav()` function bubbles this up manually. Never remove it.
- **PARTS nav active state** — uses `twx-active` class (not `w--current`) because Webflow strips `w--current` from anchor links whose `href` doesn't match the current URL. CSS rule targets `a.nav-link.twx-active`.
- **Desktop CSS must be wrapped in `@media (min-width: 992px)`** — any `display: flex !important` on desktop nav/info-bar elements without a media query forces them visible on mobile too. Root cause of previous mobile nav breakage. Always scope desktop-only styles.
- **`.nav-about-drop` is `display: inline-block` by default** — forces ABOUT to sit inline with HOME instead of full-width row on mobile. Always set `display: block !important; width: 100%` in the mobile nav section.
- **`.w-icon-dropdown-toggle` has `float: left` by default** — makes chevron appear before ABOUT text. Must override with `float: none; order: 1` and give text `order: 0`.
- **ABOUT text uses Webflow heading font** — `.text-block-30` inherits Oswald (not Arial) unless explicitly overridden. Always add `font-family: Arial, sans-serif !important` in mobile nav styles.
- **ABOUT background highlight on open** — Webflow's `.w--open` state adds a background. Must explicitly set `background: transparent !important` on `.nav-about-drop.w--open > .w-dropdown-toggle` and `:focus/:active` states.
- **Cart button must be in navbar DOM on mobile** — `position: fixed` doesn't follow the navbar's scroll-hide behaviour (Section 5 translates the navbar up). `moveCartBtnIntoNavbar()` physically moves `.open-quote-cart-btn` into `section.navbar` as a flex child on mobile so it scrolls/hides with the navbar naturally. The CSS sets `position: static` on mobile.
- **jsDelivr + browser cache after hash update** — after changing the commit hash in Webflow head/body code, do a hard reload (right-click reload → "Empty cache and hard reload") or test in incognito. The browser can still serve a stale cached version of the previous jsDelivr URL even after the URL changes. If console queries like `document.querySelector('.twx-form-row')` return `null`, the old script is still running.
- **Contact page form fields: `flex-basis` drives height in column layout** — Webflow sets `flex: 1 1 200px` inline on form row children. When `flex-direction: column` is applied (mobile stack), `flex-basis` becomes the height instead of the width, producing ~246px tall field containers. Fix: `flex: 0 0 auto !important` on `.twx-form-row > *` resets basis to content height.
- **Always push immediately after committing in `webflow-footer-scripts`** — jsDelivr serves files from GitHub. A local-only commit means jsDelivr returns a 404 HTML page for your JS/CSS request, Chrome blocks it as `net::ERR_BLOCKED_BY_ORB`, and the entire JS + CSS fails to load. Treat commit + push as a single atomic action in this repo.
- **Mobile nav regression symptoms** — if you see: old styles, no cart icon, X button not working, info header flashing, no auth links → the Webflow head/body code jsDelivr URL probably hasn't been updated to the latest commit hash, OR the `quote-cart-site-head-code.css` hasn't been pasted into Webflow Site Settings. Check both before assuming the code is broken. If Network tab shows `ERR_BLOCKED_BY_ORB` — the commit hash was never pushed to GitHub.
- **Info header flash on mobile** — `.header-information { display: none !important }` is in `global-styles.css` but that CSS is loaded async via `<link>`. The info bar briefly shows before CSS applies. Fix: add an inline `<style>` to Webflow Head Code: `@media (max-width:991px) { .header-information { display:none!important } }` so it applies before the page renders.
- **A matching commit hash doesn't prove the browser is running that code** — checking the hash in Webflow site settings only confirms what's *pasted in*, not what's actually loading. Two ways it can still be wrong: (1) the CSS `<link>` may point at the Cloudflare Worker copy instead of jsDelivr (see the `global-styles.css` Worker gotcha above) — updating the hash string does nothing if the URL itself is stale; (2) for the **portal** (a separate app, `twx-order-app`), the Webflow commit hash is irrelevant entirely — the portal deploys independently via `wrangler pages deploy`. When "the commit hash is right but nothing changed," check what's actually being served: `curl -s <url> | grep -o 'index-[A-Za-z0-9]*\.\(js\|css\)'` (portal) or check the Network tab's actual JS/CSS filenames against the source repo, rather than trusting the settings field.
- **Unclosed `<script src="...">` tag silently breaks whatever comes after it** — found 16 Jul 2026: the Webflow footer code had `<script src="...global-footer.js">` with no `</script>`, directly followed by the Tawk.to chat widget's own `<script>` tag. HTML's parser treats everything up to the *next* literal `</script>` as the first tag's inert text content — so the external `src` script still loads fine (browsers always fetch `src` regardless of body content), but the Tawk widget's inline script got swallowed as dead text and never ran. Always close external `<script src>` tags explicitly, especially when other script blocks follow in the same head/footer code field.
- **`quote-cart-info` used to show stale text on an empty cart** — `renderCart()` set its "click proceed to..." content unconditionally, before the empty-cart check, so guests/members would still see "Click proceed to..." with no proceed button present. Fixed 17 Jul 2026 — the info text now only populates in the has-items branch and is explicitly cleared in the empty branch.
- **Webflow MCP element/whtml builder tools can't create new elements inside a Symbol/Component definition** — confirmed 17 Jul 2026 while adding the footer copyright line. `data_element_builder` and `data_whtml_builder` both return "Parent element ... not found" for every element inside the Footer symbol's tree (any depth, any addressing tried: with/without `scope_component_id`, empty `component` field, Designer connected vs not, `open_canvas` vs `open_component_view`), even though `data_element_tool` (`get_all_elements`/`query_elements`) reads those exact same element IDs successfully. Reads and edits-in-place on existing elements work fine inside Symbols; only *creating brand-new* elements inside one doesn't. Workaround: add the element manually in Webflow Designer (create any styles needed via `data_style_tool` first, then apply the class name by hand) rather than looping on tool variants.
- **Verifying a `webflow-footer-scripts` change against the live site before pushing** — Playwright can drive `https://tillageworx.webflow.io/` directly and substitute a locally-edited file in place of the real jsDelivr one via `page.route('**/global-footer.js', route => route.fulfill({ body: localPatchedSource }))` (same for `global-styles.css`), so a fix can be confirmed working (or a regression caught) before it's ever committed. For logic that doesn't depend on the live page's DOM (e.g. a standalone function like `injectCartIfMissing()`), it's often more reliable to extract just that function's source and `eval()` it against a blank `page.setContent()` page instead of fighting the real page's script-load timing. `page.on('pageerror', ...)` catches uncaught exceptions the console tab would show. To find *which* code is mutating something unexpected (e.g. a class flip-flopping), monkey-patch `DOMTokenList.prototype.add/remove/toggle` to log `new Error().stack` — this is how the hamburger-stuck-as-X bug below was actually traced, not guessed.
- **`.mobile-menu` (the hamburger's Webflow wrapper) is `flex-direction: column` by default** — fine while the hamburger was its only child. `moveCartBtnIntoNavbar()` now inserts the floating cart button as a sibling right before the hamburger inside that same wrapper, so without an override the two stack vertically (144px tall) instead of sitting side by side, pushing the hamburger down and out of the visible navbar row. Fixed 19 Jul 2026 by forcing `flex-direction: row` on `.mobile-menu` in the mobile media query.
- **Hamburger icon could get stuck showing "✕" after closing the mobile nav** — traced 19 Jul 2026 via monkey-patched `classList` calls (see the Playwright gotcha above): clicking `.nav-close-btn` actually fires three handlers off one tap — our own `remove`, a redundant `remove` from the generic "close on nav link click" handler (`.nav-close-btn` is itself an `<a>` that matches that selector too), and a third handler (Section 6) that hides the menu via inline styles and then calls `hamburger.click()` "to keep Webflow's internal state in sync." That simulated click re-fires our own hamburger listener; since the class had just been removed, toggling/adding flips it straight back on. Fixed by having the close-button handler force-remove the class as the authoritative last step, regardless of what the simulated click's side effects do.
- **Cart panel + floating button markup moved from a Designer Embed element into JS** — previously lived in a Webflow Embed (class `code-embed-6`) pasted directly in the Designer; fragile, since toggling that one element's Display to "None" took out the whole cart/floating-button sitewide (happened twice, 19 Jul 2026). `injectCartIfMissing()` (in `global-footer.js`) now creates this markup itself. Its guard checks more than plain existence — `document.getElementById("quote-cart")` still finds an element hidden by `display:none` on an ancestor, so a `isHiddenByAncestor()` walk up the tree treats "present but hidden" the same as "missing," removing the stale hidden remnant and creating a fresh visible copy. The old embed can be deleted from Designer whenever convenient; the existence guard is kept only so nothing breaks if it's still on a page that hasn't been cleaned up. Dropped two unused leftovers from older cart versions while migrating: `#cart-form-slot` (nothing moves a form into it — dead since the guest-quote/member-order modals replaced the old inline-form flow) and a static `.cart-section-header` div (would have been a duplicate — `initWizard()` already creates and inserts one dynamically).
- **Customer `first_name` was inserted unescaped into `innerHTML`** in the nav "G'day" greeting (`global-footer.js`, desktop + mobile info bar) — since `user_metadata` is self-writable by any logged-in customer via the Supabase client SDK (see the `app_metadata`/`zoho_id` gotcha in the portal reference for why that matters), this was a self-XSS opening. Fixed 19 Jul 2026 by wrapping it in the file's existing `escapeHtml()` helper — but that helper lives in a different top-level IIFE (Section 2+) than `injectInfoBarAuth()` (Section 0), so a local copy had to be added to Section 0's scope rather than just calling the existing one (each top-level `(function(){...})()` in this file is a separate closure — see the `getSession()` duplication gotcha above for the same pattern).
- **A freshly JS-created floating cart button can land at the bottom of the page** — `moveCartBtnIntoNavbar()` (Section 0, docks the button next to the hamburger on mobile) runs *before* `injectCartIfMissing()` (Section 2, creates the button if the old Designer embed is missing/hidden), since the two are separate top-level IIFEs that execute in file order. If the button doesn't exist yet when Section 0's move runs, it silently no-ops and never retries — the button is just left wherever `document.body.appendChild()` put it, which visually means the very end of the page, past the footer, left-aligned. Fixed 19 Jul 2026 by redoing the same relocation logic directly inside `injectCartIfMissing()` right after creating the button, so it's correct regardless of which IIFE happens to run first. If a future change moves cart-creation earlier or the navbar-move logic elsewhere, re-check this ordering assumption.
- **`hero-para-3`'s mobile copy swap was bundled behind an unrelated early return** — `initContactPage()` wraps two independent features in one function: wrapping part of `.hero-text` into a hideable span, and swapping `.hero-para-3`'s text on mobile. The first feature used to `return` early if `p.hero-text` wasn't found — and it isn't found on the live Contact page (its markup has since changed shape), so the function always bailed before ever reaching the unrelated `hero-para-3` block. Fixed 19 Jul 2026 by decoupling the two so `hero-para-3` is always checked regardless of whether the `.hero-text` lookup succeeds. If a change to this function ever seems to "just not apply," check whether an earlier unrelated guard in the same function is returning before your code runs.
- **Locked Webflow Components (e.g. the newsletter CTA) can't be edited in the Designer canvas** — the standard workaround already used throughout this codebase is a CSS class override in `global-styles.css` targeting the component's class names with `!important`, the same pattern used for every other "Webflow's default fights us" case (ABOUT dropdown, mobile nav, etc.). Measure the live default styles first (`getComputedStyle()` on the actual elements) rather than guessing at what's off-brand — e.g. the newsletter CTA's button was already on-brand gold and didn't need touching, only the heading colour and the `Inter` font-family did.
- **Webflow's Data API can read CMS-bound custom attributes but can't write new ones** — confirmed 9 Sep 2026 building the On Sale / New Price feature. `data_element_settings_tool > set_settings` with `key: "attributes"` and a `value_binding: {source_type: "cms", ...}` entry always fails with `"value must be a string or a binding"`, even though reading an element's existing attributes (`get_settings`) shows real CMS-bound entries in that exact shape, and binding a CMS field to an element's *text content* (not an attribute) works fine through the same tool. Workaround used throughout this feature: bind a hidden text element (`display:none`, e.g. `.hidden-price-status`) instead of a `data-` attribute, and read `.textContent` from JS. This is a limitation of the API surface itself, not of Webflow generally — the same binding can be made by hand in the Designer's own Custom Attributes panel for field types that support it (Number, PlainText, etc. — just not Option/Switch, a separate, longer-standing Webflow limitation).
- **The machine wizard has its own separate hidden parts-data list, copy-pasted onto nearly every page, and it missed the whole On Sale/New Price build.** Found 9 Sep 2026 when the wizard's "Add"/"Add All Items" buttons kept adding the regular price even for parts on sale. The wizard (`global-footer.js` Section 2, `loadCMSData()`) doesn't read prices from `.add-to-quote-btn`/card hidden elements like everything else — it has its own `.part-data-item` → `.part-data-payload` collection list, and this one is a *raw HTML Embed* with old-style `{{wf:Field Name|Dynamo}}` merge tags (predates the modern per-element attribute-binding UI), not touched during the 9 Sep build. Confirmed via live DOM inspection that this embed still only exposed the old `data-sale-price`/`data-on-sale` (Switch) fields, no `data-price-status` at all. Turned out this exact embed is duplicated on ~25+ pages (confirmed present on: Home, Browse Brands, Quote Review, Find a Dealer, About Us, Privacy Policy, The Toolbox, Toolbox Posts Template, Agricast Parts, Merchandise, Merchandise Template, Tuff-Core Discs, FAQs, Terms & Conditions, Get a Quote, Pricing Update (Mar 2026), Brands Template, Parts Template — absent from Machine Configurations/Models Templates, Dealers Template, Homepage Carousels Template, Brand FAQ's Template, Search Results), since the cart/wizard is reachable sitewide and each page needs its own copy of the data. **Two Webflow API limitations blocked an automated fix:** (1) an HtmlEmbed element's raw `code` setting can't be read *or* written via the API once it contains merge-tag bindings — `get_settings` returns `{"sourceType":"unsupported","reason":"containsBindings"}`; (2) `data_element_builder` refuses to create any new element inside a Collection List item's template (`"Element is not inside a CMS context"`), even though `get_bindable_sources` confirms the right CMS fields are reachable at that scope — the same class of restriction as the Symbol-editing limitation above, just for Collection Lists instead of Components. Moni manually added one line (`data-price-status="{{wf:Price Status|Dynamo}}"`) to the embed on every page carrying it. Turned out `data-new-price` was never needed either — the existing `data-sale-price` attribute already carries the live, correct value (the field's slug `sale-price` never changed when it was renamed to "Sale / New Price", so the old merge tag kept resolving correctly under its old attribute name). Fixed in `global-footer.js` (`staging` commit `65ca544`, 9 Sep 2026) by reading `payload.dataset.salePrice` instead of the nonexistent `payload.dataset.newPrice` — `readPriceStatus()` already had a `container.dataset.priceStatus` fallback built in, so no JS change was needed for that half. **This is display-only, not a billing risk** — `worker.js` always re-resolves the real price from Zoho at order time regardless of what the cart/wizard shows. **Confirmed working end-to-end 9 Sep 2026** via live browser automation against `tillageworx.webflow.io` (Chrome DevTools MCP, with a fake Supabase session written to `localStorage` to reach the member-only price UI without a real login): drove the actual wizard (Horsch → Terrano → MT → 4m) to "Tillageworx Disc to fit Joker/Terrano", confirmed the results list showed `$135.00 → $88.50 ea, NEW PRICE`, clicked Add to Order, and confirmed the cart line item and subtotal ($88.50 × 36 = $3,186.00) used the new price correctly.
- **A Webflow site's freeform head/footer custom code has separate draft and published states, just like Designer canvas content — `set_site_freeform_code` only writes the draft.** Hit 9 Sep 2026 right after pushing the wizard price fix: updated the footer's jsDelivr commit hash via the API, reloaded `tillageworx.webflow.io`, and the old script kept loading — `curl`ing the page directly confirmed the *raw published HTML* still had the old commit hash even though `get_site_freeform_code` already showed the new one. Needed an explicit `data_sites_tool > publish_site` call (with `publishToWebflowSubdomain: true, customDomains: []` to keep it off the real domains) before the change actually reached the preview. Also caught a stale-tab issue on top of this: even after publishing, the already-open Chrome DevTools MCP tab kept serving a cached copy despite `navigate_page` reload with `ignoreCache: true` — opening a brand-new tab (`new_page`) got the fresh version immediately, so prefer a fresh tab over reloading an old one when verifying a just-published change.
- **`element.textContent = "..."` deletes ALL child elements, not just the visible text** — root cause of a nasty bug 9 Sep 2026: `gatePartsTemplate()` sets the Add to Quote/Order button's label with `btn.textContent = "Add to Order"`, which silently wiped out the `.hidden-price-status`/`.hidden-new-price` divs living inside that same button on every page load, before a customer ever clicked anything. The cart quietly fell back to the item's regular price with no error, so this looked exactly like a data-wiring bug and took real digging (a live before/after test in Chrome DevTools) to actually trace. Any code that needs to update a button/element's visible label while it also carries hidden data children must capture and re-append those children first — see `setButtonLabel()` in Section 0 — never a bare `textContent` reassignment on an element that might have meaningful children.
- **A native Webflow Designer style can silently defeat a CSS override that only changes padding** — the `.add-to-quote-btn` class (defined directly in the Designer, not in `global-footer.js`) hardcodes `height: 50px` and `width: 195px`. Reducing `.twx-view-price-btn`/`.twx-contact-btn`/`.twx-member-add`'s padding via the injected CSS had zero visible effect on button height, because padding only affects layout size when height is otherwise `auto` — nothing was overriding the explicit `height`. Fix needed an explicit `height: auto` added to the override rule (specificity alone was enough — the injected rule's selector is already more specific, no `!important` needed). If a padding change to a `.add-to-quote-btn`-based element doesn't visibly do anything, check for a competing `height`/`width` set directly on the native class in the Designer (`data_style_tool > query_styles`) before assuming the CSS didn't apply.
- **`.twx-sale-badge` needed an explicit `line-height: 1`** — without one, it inherited the page's ambient `line-height: 20px` against its own 9px font, making the badge 24px tall no matter how small the padding was set. Confirmed via `getComputedStyle()` in the browser before guessing at a fix — the same approach caught the height:50px issue above.
- **The member order modal's pre-submit screen had no price/total display at all, and the post-submit screen's Total was a hardcoded string, not a calculation.** Found 9 Sep 2026 investigating a report that "the order confirmation page" was only showing description and quantity. Two separate gaps in `openMemberOrderModal()`: (1) the pre-submit "Place Your Order" screen's `cartSummaryHtml` builder only ever rendered `item.name` and qty — never had a price column, so a customer confirming their order before submitting saw no pricing whatsoever, even though the cart panel right behind it (still visible) did; (2) the post-submit "Order Submitted!" screen correctly computed and displayed Subtotal, but its Total row's markup was the literal string `"TBA"`, never actually calculated, even when the subtotal was fully known. Fixed by extracting a `computeCartPricing(cartArr)` helper (mirrors the cart panel's own subtotal/GST/total math — `item.priceStatus ? (item.newPrice || item.price) : item.price`, then `× qty`, then `× 1.1` for GST) and using it in both places. Freight remains hardcoded "TBA" in both screens since it genuinely isn't known until Moni adds it in Zoho — only Subtotal/GST/Total are calculated. Verified via live browser automation (fake Supabase session + mocked `fetch` so no test order hit production Zoho) against both the `tillageworx.webflow.io` staging preview and, after merging, production. `webflow-footer-scripts` commit `49707d4`.
- **Editor format-on-save can make an unrelated one-line edit look like the whole file changed** — happened 20 Jul 2026: a manual one-line edit to `global-footer.js`, saved from an editor with Prettier (or similar) format-on-save enabled, reformatted line-wrapping across the *entire* file and flipped line endings to CRLF, while everything in git history is LF. `git diff` then showed ~650 changed lines for what was actually a single real edit. Fix: `git checkout -- global-footer.js` to discard the noisy working-copy version (safe as long as you've identified the real intended change first, e.g. via `diff <(git show HEAD:file) <(tr -d '\r' < file)` to isolate content changes from line-ending noise), then reapply just that one change directly. Longer-term fix on Moni's end: disable format-on-save for this repo, or set `"files.eol": "\n"` in VS Code so saves stop flipping to CRLF.
